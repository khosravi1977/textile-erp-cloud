# بازبینی معماری و اجرای فاز چندشرکتی

## جمع‌بندی تصمیم

برای وضعیت فعلی پروژه، معماری انتخاب‌شده این است:

- یک پایگاه داده PostgreSQL مشترک
- جداسازی داده‌ها با ستون `company_id`
- احراز هویت با JWT
- ثبت لاگ حسابرسی در دیتابیس
- کنترل دسترسی کاربر و تب‌ها بر اساس نقش و مجوز
- آماده‌سازی مسیر ارتقا به معماری‌های سنگین‌تر در آینده، بدون تحمیل پیچیدگی زودهنگام

این تصمیم نسبت به مدل‌هایی مثل `schema-per-tenant` یا دیتابیس جدا برای هر شرکت، برای این پروژه مناسب‌تر است؛ چون پروژه در حال توسعه سریع است، بخش مالی و عملیاتی باید یکپارچه شوند، و نگهداری migrationها و گزارش‌ها باید ساده و قابل کنترل بماند.

## نقاط ضعف معماری قبلی و اصلاح انجام‌شده

1. فقط اضافه‌کردن `company_id` کافی نبود؛ کوئری‌ها باید حتماً tenant-aware باشند.
2. ورود با رمز ثابت یا حالت توسعه دائم برای محیط واقعی خطرناک بود.
3. لاگ ساده کنسولی برای حسابرسی مالی کافی نبود.
4. هم‌زمانی ویرایش در جداول مالی باید با `version_number` قابل کنترل باشد.
5. اجرای مالی و عملیاتی باید به PostgreSQL و Go/React نزدیک شود تا اختلاف تکنولوژی کمتر شود.

## اصلاحات اعمال‌شده

- جدول `companies` ایجاد شد.
- ستون `company_id` به جداول مهم مالی اضافه شد.
- ستون `version_number` برای کنترل تغییرات هم‌زمان اضافه شد.
- جدول `audit_logs` برای ثبت درخواست‌ها ایجاد شد.
- JWT با `JWT_SECRET` امضا و اعتبارسنجی می‌شود.
- اطلاعات `company_id`, `user_id`, `role`, `request_id` در context درخواست نگهداری می‌شود.
- ورود مالی از جدول واقعی `users` انجام می‌شود.
- رمز اولیه مدیر مالی از `FINANCIAL_ADMIN_PASSWORD` خوانده می‌شود.
- رمز اولیه مدیر عملیاتی از `OPERATIONAL_ADMIN_PASSWORD` خوانده می‌شود.
- حالت توسعه `X-Dev-Mode` فقط با `ALLOW_DEV_AUTH=true` فعال می‌شود.
- API key فقط با مقدار معتبر `FINANCIAL_API_KEY` پذیرفته می‌شود.
- ریپازیتوری‌های اصلی مالی بر اساس `company_id` فیلتر شدند.
- اجرای کلی پروژه در `run_server.bat` به سمت PostgreSQL، Go و React تنظیم شده است.

## کارهای باقی‌مانده برای تکمیل ۱۰۰٪ معماری قبلی

1. tenant-aware کردن تمام endpointهای باقی‌مانده‌ای که هنوز مستقیم یا in-memory کار می‌کنند.
2. تکمیل سطح دسترسی تب‌ها در هر دو بخش مالی و عملیاتی.
3. افزودن تست API برای جلوگیری از نشت داده بین شرکت‌ها.
4. تکمیل audit برای عملیات حساس مثل حذف، ویرایش فاکتور، تسویه، واگذاری چک، ورود/خروج انبار.
5. افزودن صفحه مدیریت شرکت، شعبه، کاربران و مجوزها به رابط کاربری نهایی.

## مسیر اجرای پیشنهادی بعدی

ابتدا باید تمام مسیرهای فعال مالی و عملیاتی با `company_id` تست شوند. سپس صفحه مدیریت کاربران و دسترسی‌ها به‌صورت واقعی به دیتابیس متصل شود. بعد از آن می‌توان سراغ امکانات پیشرفته‌تر مثل گزارش مدیریتی چندشرکتی، پشتیبان‌گیری خودکار، و کنترل سطح دسترسی ریزدانه رفت.
