# ناظر مالی — محدوده، آزمون و انتشار

## رفتار جدید

- تب ناظر مالی، گزارش سمت سرور از ارتباط هزینه، گردش، فاکتور، چک، موجودی و حسابیار را نشان می‌دهد. نتیجه ناقص یا خطای اتصال هرگز به عنوان سلامت نمایش داده نمی‌شود.
- هزینه‌های عملیاتی با مبلغ، تاریخ، گروه/زیرگروه، ثبت‌کننده، شرح و شماره سند تطبیق داده می‌شوند؛ هسته حسابیار بدون سقف فهرست ۵۰۰تایی پیمایش می‌شود.
- دفتر ذخیره‌شده WS با خالص اسناد مالی مقایسه می‌شود. این گزارش حسابرسی رسمی یا تضمین صحت تصمیم‌های انسانی نیست؛ قاعده‌محور است و داده‌ای به سرویس هوش مصنوعی بیرونی ارسال نمی‌کند.
- پایش مستقل سرور هر پنج دقیقه فقط گزارش تشخیصی ذخیره می‌کند. هیچ تراکنش یا مانده‌ای را خودکار اصلاح نمی‌کند.
- فاکتور ورود: پیشنهاد نرخ از سابقه هم‌کالا/واحد/ارز، اولویت فروشنده یکسان؛ سپس پیش‌نمایش اثر واقعی موتور حسابداری و تأیید صریح. قیمت قطعی بازار یا پیشنهاد تشخیص مالکیت نیست.
- تأیید به کاربر، شرکت، نسخه، تمام پیش‌نویس و سند مبدأ متصل است؛ ده دقیقه اعتبار دارد. تغییر/انقضا/تکرار نسخه پذیرفته نمی‌شود. فاکتور، سند حسابداری و سابقه تأیید در یک تراکنش DB ذخیره می‌شوند.
- ناظر اجازه نوشتن ایجاد نمی‌کند. دسترسی ثبت همان مجوز قبلی فاکتور ورود است. کنترل‌های قطعی روی مسیر مشترک ذخیره UI، حسابیار و همگام‌سازی عملیاتی اعمال می‌شوند؛ نقص قدیمی تغییرنکرده مانع کار نامرتبط نمی‌شود.

## آزمون‌ها و محدودیت شواهد

- `financial: go test ./...` شامل قواعد حسابداری، چرخه چک، هزینه و موبایل و آزمون‌های جدید تأیید و رابطه والد/فرزند.
- آزمون PostgreSQL در `tests/integration/supervisor_persistence_test.go`: پیش‌نمایش بدون نوشتن، رد دستکاری، ثبت و آرتیکل دقیقاً یک‌بار، سابقه تأیید، رد تکرار و نسخه منقضی. فقط با TEST_POSTGRES_DSN اجرا می‌شود؛ نبود DSN یعنی skipped نه موفقیت آزمون دیتابیس.
- `financial/web: npm run build`؛ واحدها و تبدیل واقعی Vite.
- `financial/web: npx playwright test`؛ همه تب‌های مجاز بدون خطای JS، تاریخ شمسی و چرخه پیش‌نمایش/تأیید/بازخوانی با API آزمایشی، و عدم اعلام سلامت هنگام قطع اتصال. API ساختگی این آزمون اثبات ذخیره تولیدی نیست؛ آزمون DB جدا است.
- هیچ داده واقعی مشتری در تست‌ها مصرف، ایجاد یا حذف نمی‌شود. صحت تمام ترکیب‌های ممکن فیلدهای تمام تب‌ها و تمام مانده‌های تولیدی صرفاً با این آزمون‌ها قابل ادعا نیست؛ آزمون پذیرش زنده پس از تأیید انتشار لازم است.
- فعلاً سقف تطبیق هزینه‌های عملیاتی ۱۰۰۰۰ ردیف است؛ رسیدن به سقف، پوشش ناقص اعلام می‌شود. صف آفلاین خود گوشی تا زمان رسیدن به سرور قابل بررسی نیست.
- پیشنهاد نرخ و پیش‌نمایش تأیید مخصوص فاکتور ورود است؛ تب‌های دیگر از کنترل ذخیره و گزارش ناظر استفاده می‌کنند، نه گردش تأیید جدید.

## انتشار و بازگشت

این شاخه باید پس از موفقیت CI و تأیید مالک به main ادغام شود؛ تصاویر immutable و استقرار از workflow رسمی انجام می‌شود. قبل از آن روی تولید مستقر نیست.

مهاجرت ۰۲۱ فقط دو جدول گزارش و سابقه تأیید اضافه می‌کند؛ هیچ مبلغ یا داده تولیدی بازنویسی نمی‌شود. rollback با تصویر قبلی و حفظ جداول حسابرسی انجام شود. down عمداً جدول را حذف نمی‌کند. اگر مهاجرت موفق نشود، تأیید جدید باید fail-closed بماند.

کلید امضای پیش‌نمایش فقط در حافظه فرایند است؛ راه‌اندازی مجدد یا انتقال درخواست به replica دیگر مستلزم پیش‌نمایش مجدد است. برای استقرار چند replica نیاز به کلید مشترک امن یا sticky routing دارد؛ داده محرمانه نباید در مخزن ذخیره شود.
